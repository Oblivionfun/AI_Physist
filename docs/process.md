# 研发过程记录（汇报用）

本文按时间顺序记录这个项目是怎样做出来的：每个阶段做了什么、遇到了什么问题、依据什么做判断、方向因此怎样调整。每个节点都附有证据指针，可以对照查看：

- 决策编号（D-xxx）见 [`decisions.md`](decisions.md)；
- 逐次的工程细节和验证命令见 [`worklog.md`](worklog.md)；
- 提交记录用 `git log` 查看；
- 运行目录在 `~/mlab-runs/<run-id>/`，导出的演示在 `demo/recorded/`。

## 一页摘要

- **题目在考什么。** 题目表面上是“一个 Agent 造机器、另一个 Agent 学会用”，本质上是三个研究问题的交叉：出题者和解题者如何共同演化而不退化；解题者如何通过主动实验推断隐藏的物理量；两个隔离的 Agent 之间，什么样的信道只传递“难度信号”而不传递“答案”。
- **核心设计。** 由一个持有真值的可信裁判充当唯一中介。“题目可解”不靠出题者自觉，而由裁判出具可验证的证书：知道参数就能解、不知道参数就解不了、靠实验学得会。“学会了”也不靠学习者自报，而由裁判拿真值检验它提交的可执行理论，并做孪生互换测试。
- **过程中最重要的几次转向：**
  1. 结合出题实验室的背景做对抗性反思后，重心从“隔离的安全工程”转向“建造的物理合理性 + 学习者理论的质量”。
  2. 用户质疑“用两家厂商隔离”是否必要。实测后结论是：换厂商既不必要也不充分，真正的泄漏通道在工具层。于是改为统一运行时加系统级沙箱。
  3. 评审另两份方案时发现 gemini 的实现把答案写进了学习者代码，由此定下六条红线。
  4. 实现中，证书两次拦下系统作者（我）自己手写的“合格”设计；一次真实运行中，建造者 Agent 自己诊断出裁判 C3 的统计缺陷。这些都推动了裁判本身的修正。
- **当前结果（demo-1，3 轮）。** 三轮装置都由建造者自主设计并一次通过认证。学习者前测都是 0%，考试 75% 到 100%。孪生互换测试三轮都是“自己的理论在自己的实例上有效、换到孪生实例上为 0”。黑盒对照从 100% 降到 62.5%，说明建造者确实在往“需要理解物理”的方向升级题目。学习者学会了“用”，但物理参数辨识得不准，改装检验暴露了这一点。

## 阶段 0：理解题目（11-05 21:46 至 22:00）

**做了什么。** 先读了几份科研方法类 skill（研究计划、选题评估、实验设计、假设生成），再检查本机环境：系统 Python 是 3.9，没有 MuJoCo，有 uv；没有任何 LLM API key；codex 和 cursor-agent 两个 CLI 已登录，支持无头模式。

**得出的判断。** 题目是三条研究线的交叉：

1. **无监督环境设计（UED）**，代表工作有 PAIRED、POET、OMNI-EPIC。出题者和解题者共同演化，经典的失效模式是出题者退化，专出无解题或噪声题。
2. **主动实验与自动科学发现**，代表工作有 BoxingGym、PHYRE。解题者要通过干预和观测推断隐变量，再据此行动。
3. **信息隔离下的机制设计。** 唯一允许的信道必须能传递难度信号，又不能泄露答案的信息量。

由此得到三对必须同时处理的张力：隔离与协作、困难与可解、“真学会”与“碰运气或靠先验”。

**核心洞见。** 一个好的挑战，等于“解对隐藏参数敏感”乘以“隐藏参数能从接口辨识出来”。这两点都可以由持有真值的裁判定量检验。所以“避免无解”可以落成三张证书：存在性（知道真值能解）、必要性（不知道就解不了）、可辨识性（预算内能从公开接口推断出来）。

**方向选择。** Agent 用什么实现会大幅影响架构，所以我问了用户一个问题。用户选择“LLM CLI 混合”：建造者用 codex，学习者用 cursor-agent，另设脚本对照组。（这个选择后来在阶段 3 被修改。）

## 阶段 1：结合出题实验室背景做对抗性反思（22:00 至 22:08）

**触发。** 用户补充说，题目来自西湖大学吴泰霖的 AI4S 实验室，要求对方案做对抗性的独立反思。

**调研。**
- 实验室在 ICML 2026 发表的 [BuildArena](https://arxiv.org/abs/2510.16559)，让 LLM Agent 在物理仿真里造机器。论文自己承认的局限正好对应本题的要求：缺少“基于仿真结果的外层闭环改进”（对应多轮迭代）；组件库多样性不足（对应通用组件）。
- 导师博士期间的 [AI Physicist](https://arxiv.org/abs/1810.10525) 定义了他心中的“学习”：学小而专的理论，带适用域，用奥卡姆剃刀挑选，存进理论库终身复用。
- 以上关联是根据公开论文做的推断，不是出题人的原话。

**发现原方案的问题，以及改法：**

| 问题 | 改法 |
|---|---|
| 建造的物理合理性没抓住要害：MuJoCo 很容易作弊，比如零件悬空焊在世界上、关掉碰撞、凭空施力 | 建造者不写任意代码，改用 BuildArena 式构造 API，每一步都检查碰撞、连接、支撑 |
| 每轮重采样全部隐藏参数，跨轮记忆测不出东西 | 物性分两层：零件和材料的物性整场固定，装置专属量按实例抽取（D-005） |
| 只测分布内预测，分不清“拟合曲线”和“辨识物理” | 学习者提交可执行理论 `predict.py`，在外推和公开改装后接受检验 |
| 纯噪声任务的成功率接近 50%，看起来“难度正好”；刀锋式任务在 BuildArena 里几乎全军覆没 | 要求 oracle 在噪声下仍能解，并新增鲁棒裕度证书 |
| 我自己也是泄漏源：看过装置后再调学习者 prompt，就把信息带了过去 | 学习者 prompt 在任何装置产生之前冻结，并记录哈希 |

**方向变化。** 原方案偏重隔离的安全工程，科学内容偏弱。反思后，重心转向两件事：建造的物理合理性，以及学习者理论的质量。

## 阶段 2：调研可借鉴的开源方案（22:08 至 22:13）

按“直接用 / 借思路 / 不借”整理：

- **计划直接用：** MuJoCo 的 `MjSpec`；Anthropic 的 sandbox-runtime（`srt`）；PHYRE 的“稳定解”定义。
- **借思路：** BuildArena 的构造工具分组和逐步检查；PhysGym 的先验分级；NewtonBench 的“物性偏离教科书”；BoxingGym 的信息增益；METR 的“评测放在沙箱外”；OMNI-EPIC 的版本档案。
- **不借：** Inspect（依赖 Docker）、`sbi`（依赖 torch）、MCP 工具（学习者需要在脚本里批量调用实验）。

**后来被实现推翻的两项：**
- `MjSpec` 改为“自定义 IR 加 MJCF XML”（D-003）。理由是构造记录要能序列化、计算哈希、做 diff 和回放，而改装检验需要改尺寸后重新编译。
- `srt` 改为手写 Seatbelt 策略（D-013）。理由是它需要全局安装 npm 包，网络代理和 Node 的兼容性未经验证；而 deny-list 策略可以用自检逐条验证。

## 阶段 3：用户的四个追问带来的修正（22:13 至 22:38）

用户没有相关学术背景，先请我循序渐进地讲解思路，随后提了四个问题。

1. **“学到了什么，是不是就是记忆？”** 从存储方式看是的：模型参数不变，学习全部发生在上下文和它自己写的文件里。但“记住”和“学会”不同：流水账答不了没试过的情况，而“参数估计 + 规律 + 可运行的预测程序”可以外推。评测因此专门考外推、改装和孪生互换。
2. **“有必要用两家厂商吗？”** 用户的质疑是对的。我实测本机：codex 的 `memories` 功能默认开启，磁盘上有数百份明文会话记录。结论是换厂商既不必要（权重不会因对话改变），也不充分（学习者照样能用 shell 读对方的会话记录）。**方向调整：** 统一用 cursor-agent，模型作为可配置变量；隔离靠关闭记忆、全新会话、沙箱禁读对方记录、canary 审计（D-002）。
3. **“裁判会不会过拟合、误拦？用代码还是 LLM？”** 裁判本质是一个分类器，会误拦也会误放。对策是：硬规则少而讲原理；成功率分“通过 / 灰区 / 不通过”三档；准备带标签的合格与作弊样例，像测分类器一样测裁判（元评测）；能用代码判的就用代码，因为代码不会被建造者的文字说服。
4. **“Agent 就是写 prompt 吗？”** 不只是。Agent 等于“模型 + 工作环境”：工具、可见范围、记忆结构、由代码强制执行的流程规则、可操作的报错、固定的交付格式。prompt 只决定它想做什么，工具和规则决定它能做什么。

## 阶段 4：评审 codex 和 gemini 的方案，形成终极方案（22:38 至 22:48）

- **codex：** 只有设计文档，没有实现，但设计质量高。采纳了“每次实验先预测再看结果”“孪生实例互换理论”“以实例为统计单元”“考试每个目标只有一次机会”。没有采纳它对 API key 的依赖，也没有采纳用 Python 审计钩子做隔离（官方文档明确说过审计钩子不是沙箱）。
- **gemini：** 有完整实现，图表漂亮，但核心结论站不住。读代码发现：
  - 两个“Agent”都是手写脚本；
  - 建造者的“初稿无解、自动修复”是写好的剧本；
  - 学习者代码里写死了针对具体装置的解法分支和物理常数；
  - 报告里的 R² 被人为设了下限。

  它展示的“学习者发现了闸门”，实际上是作者把答案写进了学习者，泄漏通道是作者本人。这些被定为本项目的六条红线（`AGENTS.md` 第 2 节，D-008），由测试覆盖。
- **输出：** [`终极方案.md`](../终极方案.md)，提出六条原则，每条针对一个具体漏洞。

## 阶段 5：建立约定，实现物理核心 M1（22:48 至 23:55）

**先建约定再写代码。** 建立 `AGENTS.md`（依赖方向、红线、风格、提交格式）、决策记录（D-001 至 D-010）和工作日志；代码仓库按用户指定设为 `Oblivionfun/AI_Physist`。

**实现：** 零件目录与物性先验、构造 API（每步做物理检查）、编译器、仿真运行器、证书 C0 到 C3、两台合格夹具和 10 个作弊装置。

**遇到的问题和转向（D-011）：**
- MuJoCo 的父子碰撞过滤对“焊接到世界的父体”不生效，销钉被误判为穿模。改为每个零件一个刚体，并精确排除每对销钉连接的碰撞。
- 摆锤的目标区间在先验的某个角点不可达，被 C1 正确拦下。这说明证书在工作，于是把夹具改到全先验可达的范围。
- 步长减半后，命中解的结果偏移达到 0.5 到 1 倍容差，这是软接触的一阶误差。把步长改为 0.001 s；收敛检查只在命中解上做，因为旋钮空间别处的混沌是合法物理。
- 灰盒参考学习者用梯度法只命中 2/8，因为接触让目标函数不光滑。改为粗搜索加 Nelder-Mead 后命中 8/8。
- 弹簧发射台几乎打不出钢球：软接触需要约 20 ms 传递动量，而活塞到端部止挡才撞上钢球；50 Hz 采样又把振荡混叠成了缓慢爬行。重新设计了发射台。

## 阶段 6：裁判协议与离线闭环 M2（至 11-06 00:50）

**实现：** 学习者协议状态机、自动生成的说明书、泄漏扫描、哈希链信道日志、理论评测、成绩单、与装置无关的脚本学习者、离线闭环。

**遇到的问题和转向（D-012）：**
- **我手写的“合格夹具”其实太简单。** C2 只在先验上抽 2 到 3 个实例时，结果在 0.33 到 0.88 之间摆动。用大样本（160 次）估计后发现，两台夹具的名义成功率约为 0.39 和 0.41，高于 0.3 的阈值，之前能通过只是采样噪声。于是把先验抽样增加到 24 个实例，并把目标区间移到对隐藏量敏感的区域。**教训：** 不能信任出题者的自觉，包括系统作者本人。
- 发射台没有装置专属的隐藏量，两个孪生实例物理完全相同，互换测试恒为 1.0。改为标注“不具信息量”，并引导建造者加入装置专属量；孪生实例改为对偶采样。
- 脚本学习者把上一实例的原始数据混进本实例的模型，第 3 轮考试只有 12%（无记忆对照为 100%）。说明跨轮记忆应保存可迁移的知识，而不是绑定于实例的数据。

## 阶段 7：系统级隔离与 LLM 运行时 M3（至 01:30）

**实现：** 按角色生成的 Seatbelt 沙箱策略和自检、带能力令牌的 Unix socket RPC、学习者用的 `lab` 客户端（只用标准库）、建造者用的 `forge` 工具、cursor-agent 后端、冻结的 prompt。

**踩过的坑。** 每一个都是“意想不到的共享资源或系统行为”，都是实测发现的：
- 宽泛的写放行写在禁令之后，把禁令覆盖了。改为分层渲染策略。
- 可编辑安装的 `.pth` 指向被禁读的项目目录，Python 导入时直接抛错。改为给学习者单独建一个不含 mlab 的 venv。
- cursor-agent 的 shell 工具要逐级解析祖先目录，而祖先目录被禁读。改为只对祖先链放行元数据读取。
- Node 启动时会 stat 标准输出，输出文件在被禁读目录下就会直接崩溃。改为管道输出。
- 每个工作区共用的聊天目录被启动快照误列入禁读。改为精确排除 Agent 自己的目录。

## 阶段 8：第一次真实 LLM 运行（11-06 午后）

- composer-2.5 在任何目录下都不调用工具（不加沙箱也一样），属于模型服务的问题。换用 gpt-5.3-codex、claude-opus-5、gpt-5.6-sol，都正常。
- **建造者第一次提交被 C2 拒绝后，第二次会话把一个多小时全部用来循环本地检查，始终没有再提交。** 由此加入会话截止时间：`forge` 每条命令都显示剩余时间，C2 贴近阈值时标注 BORDERLINE（D-014）。
- **学习者冒烟运行：** 考试 8/8，但理论在改装检验上 0%。这是“学会用但没辨识物理”的第一个实证，说明改装检验确实有区分力。
- 学习者把目录型号的属性误当成实例专属，原因是说明书没讲清楚。于是任务卡为每个未知量标注作用范围（D-015）。
- **demo-1 刚启动，建造者就往 `/tmp` 写了文件。** `/tmp` 是两个 Agent 都能读写的共享目录，构成泄漏通道。于是封闭共享临时目录，自检增加到 32 项，并停掉 demo-1 重新启动（D-016）。

## 阶段 9：正式演示 demo-1（17:02 至 18:25）

**配置：** 建造者用 claude-opus-5-thinking-high，学习者用 gpt-5.6-sol-high；3 轮；FULL 认证；每个会话 40 分钟。

| 轮次 | 装置 | 旋钮 / 预算 | 前测 A/B | 考试 A/B | 互换（自己 / 孪生） | 黑盒对照 |
|---|---|---|---|---|---|---|
| 1 | stop_catapult | 2 / 80 | 0% / 0% | 100% / 75% | 0.875, 0.625 / 0, 0 | 100% |
| 2 | spring_stop_catapult | 3 / 62 | 0% / 0% | 100% / 100% | 0.75, 0.5 / 0, 0 | 75% |
| 3 | wide_mass_catapult | 3 / 62 | 0% / 0% | 100% / 88% | 0.75, 0.5 / 0, 0 | 62.5% |

**看到了什么：**
- **建造者按反馈升级。** 第 1 轮成绩单说“黑盒也能满分，可以被暴力拟合”。第 2 轮它加入一根与电机增益相互混淆的扭簧和第三个旋钮，预算降到 62。它还在本地自检中发现参考学习者掉到 4/6，于是回调了预算。
- **学习者跨轮适应。** 第 1 轮笔记写下“下次先在低能量区校准，再把预算花在辨识上”，第 2 轮照做。它设计对称移动滑块的实验，推出转动惯量比约 1.56。世界级参数的估计在三轮之间沿用。
- **学会用，但没辨识准物理。** 电机增益的相对误差为 0.2 到 0.29，钢的滚动阻力偏差约 3 倍，挡块改装检验 0%。
- **反馈通道真的被用上了。** 学习者通过 field ticket 报告“每条命令都附带 zsh 报错”。原因是 zsh 的 heredoc 临时文件默认写在 `/tmp`，而上一步刚封闭了 `/tmp`。修复后在沙箱内验证。
- 隔离审计 clean；哈希链日志 15 条，校验完整。

## 阶段 10：从真实运行反查裁判（18:25 至 23:40）

这一阶段的三个问题都不是事先想到的，而是从 Agent 的真实行为里暴露出来的。

**1. C3 参考学习者基本是在抛硬币（D-017）。**
- **线索：** 第 3 轮建造者在设计日志里写道，它的两台新机构被 C3 拒绝，并且“预算越多成绩越差”，同一结构在不同种子下 6/6 和 1/6 都出现过。它的判断是“C3 被种子噪声主导”。
- **第一次诊断走了弯路：** 我想比较“拟合解的代价”和“真值的代价”，以区分“优化器没找到”和“数据不够”。但 C3 只拟合排名前几的参数，其余参数固定在先验中心，在这个简化模型里真值并不是最优点，比较没有意义。
- **改为控制变量实验：** 在第 3 轮装置上各跑 8 个种子。

  | 参考学习者配置 | 平均命中率 | 最差一次 | 达到 0.7 的次数 |
  |---|---|---|---|
  | 原 FAST 预算（16 个搜索点，1 次重启，24 次评估） | 0.65 | 0.00 | 3/8 |
  | 加大优化器预算（32 个搜索点，3 次重启，80 次评估） | 0.88 | 0.83 | 8/8 |
  | 同上，并拟合 4 个参数 | 0.94 | 0.83 | 8/8 |

- **结论：** 方差主要来自拟合器的计算预算。原配置下，建造者用 `forge check` 自检时 C3 等于抛硬币，它放弃的两台机构很可能是被误杀的。另一个问题是只做一次拟合，所有目标都依赖这一次拟合，统计上过于乐观。
- **修复：** 加大并统一拟合预算，FULL 做两次独立拟合，证书按拟合报告。
- **回头验证：** 建造者放弃的两台设计没有存档，但它的会话记录里留有每次编辑后的完整文件。我从中还原出这两台设计，在同一个世界下用修复前后两种配置各认证 3 次。
  - “释放滑块”从 5、5、2（满分 6）变为 5、6、5，修复后稳定通过。建造者归纳的“阶段时长旋钮无法拟合”其实是被裁判噪声误导的结论，它因此封掉了一整类升级方向。
  - “断电滑行”从 2、6、5 变为 2、4、6，**仍然对种子敏感，这个问题没有完全解决**，已作为未解决项记入 D-017。

**2. 改装检验可能没有区分力（D-018）。**
- **线索：** 第 3 轮挡块改装的影响恰好是 0.0。
- **复现：** 挡块外移后撞杆扫不到它，摆臂由铰链自身的限位停下。这时忽略改装的黑盒反而得分，按物理推理预测变化的学习者却被判失败。
- **修复：** 认证新增改装检验（影响不足 1.5 倍容差则退回）；运行时把无区分力的考题标注出来，不计入失败标签；元评测增加对应的作弊装置。
- **新检查拦下了我自己的摆锤夹具。** 原因是两个效应相互抵消，影响只有 0.44 倍容差。这是继阶段 6 之后，系统作者的“合格”设计第二次被证书拦下。

**3. 网络故障被计成学习者 0 分（D-019）。**
- **经过：** 两组对照（较弱模型、记忆消融）并行运行时，本机 DNS 中断，之后的会话几秒内就退出，被照常计为考试 0%。
- **为什么要修框架：** 这类失败和学习者能力无关，但表面上与“学习者失败”无法区分，会直接污染结论。
- **修复：** 识别网络或服务类错误，退避重试（不占用催促次数）；仍失败的会话标记为无效、不计分。
- **处置：** 作废的对照保留为 `*-netfail` 目录作为留痕，在修复后的代码上顺序重跑。

## 贯穿全程的几条体会

1. **不信任出题者的自觉，包括系统作者自己。** 我手写的合格夹具两次被自己的证书拦下（D-012、D-018）。
2. **裁判也会错，需要被测试。** 元评测用带标签的合格与作弊样例检验裁判的误拦和误放。最有价值的裁判缺陷，是在真实 Agent 的行为里暴露的：建造者 Agent 自己诊断出 C3 的统计问题。
3. **隔离漏洞多出现在意想不到的共享资源上：** `/tmp`、zsh 的 heredoc 临时文件、聊天目录、IDE 会话历史、可编辑安装的 `.pth`。这些都靠实测和自检发现，而不是靠事先推理。
4. **区分“能力失败”和“基础设施失败”。** 否则断一次网就会制造出虚假的结论。
5. **演示中的失败必须真实。** 被拒的提交、学习者的失败、对照组的作废都来自真实运行，没有一处是安排的剧本；这正是 gemini 实现的反面教训。
6. **“会用”和“理解”是两件事，评测要能把它们分开。** 学习者考试接近满分，但改装检验和参数估计显示它并没有辨识出物理。
