## D-001 独立工作区与仓库
- 日期：2026-11-05；状态：Accepted
- 背景：工作区里已有 `codex/`（只有设计文档）、`gemini/`（有实现），根目录下还有 gemini 代码的副本。
- 决策：`claude/` 自成一体，拥有独立的 git 仓库和 venv，不 import 上述任何代码。
- 理由：评审中发现 gemini 的学习者里写死了针对具体装置的解法；复用它的代码会把这种泄漏一起带进来。

## D-002 Agent 运行时：统一 harness，模型按角色配置
- 日期：2026-11-05；状态：Accepted
- 决策：默认后端为 `cursor-agent -p`（本机已登录，不需要 API key），建造者和学习者分别配置模型；codex CLI 作为可选后端；scripted 后端只用于离线复现和 CI。
- 理由：模型权重不会因为一次对话而改变，跨 Agent 的泄漏只可能发生在工具层。实测本机 codex 的 `memories` 功能为 stable 且默认开启，磁盘上有数百份明文会话记录。因此用不同厂商来隔离既不必要也不充分，需要做的是关闭记忆、使用全新会话，并由沙箱禁止读取对方的会话目录。
- 影响：沙箱策略必须覆盖 `~/.codex`、`~/.cursor/projects/*/agent-transcripts` 和 `~/.cursor/plans`。

## D-003 构造层采用 IR -> MJCF XML，而不是直接驱动 MjSpec
- 日期：2026-11-05；状态：Accepted（偏离方案 2.2 中“包装 MjSpec”的表述）
- 决策：建造者调用构造 API，生成可序列化的 `DeviceIR`（pydantic）；编译器把 IR 转成 MJCF XML，再由 `mujoco.MjModel.from_xml_string` 编译。
- 理由：
  - 构造记录可以序列化、计算哈希、做 diff 和回放，它就是“留痕”；
  - 裁判的改装检验需要修改可见尺寸后重新编译，用 IR 实现最简单；
  - MuJoCo 的 XML 编译器会做同样的语义检查；
  - 可以避免依赖仍在演进的 MjSpec Python API 细节。
- 影响：逐步校验在“IR 加增量编译”上完成，效果上等价于包装 MjSpec。

## D-004 任务采用声明式定义，计分路径中不执行建造者代码
- 日期：2026-11-05；状态：Accepted
- 决策：任务由以下几部分声明：旋钮（knobs）、动作程序模板（phases）、结果量（outcome）、目标空间（goal space）、容差（tolerance）、时长（horizon）。由裁判计算结果和成功与否。存在性证书默认使用裁判的通用搜索型 oracle（已知真值，在旋钮空间里搜索）；建造者自定义 oracle 作为可选项（P1）。
- 理由：
  - 计分路径里不执行建造者代码，就杜绝了注入，也杜绝了建造者在计分里做手脚；
  - 通用 oracle 让存在性证明不依赖建造者自觉；
  - 低维旋钮让 LLM 学习者和脚本基线都容易操作。
- 影响：结果量只支持一组白名单类型：落地点、终态位置、最大高度、终态关节角。

## D-005 物性分层：theta_world 整个 run 固定，theta_device 按实例采样
- 日期：2026-11-05；状态：Accepted
- 决策：零件目录的隐藏物性（材料摩擦、滚动摩擦、铰链阻尼与摩擦损失、弹簧劲度、电机增益）由裁判在每个 run 采样一次；装置专属的隐藏量（例如密封盒质量）由裁判按实例采样。建造者只能看到先验范围。
- 理由：这样跨轮记忆才有价值，也构成组合迁移测试；而且建造者在结构上不可能泄露数值答案。

## D-006 学习者评测协议
- 日期：2026-11-05；状态：Accepted
- 决策：每个实例依次经过：前测（3 个一次性目标）、实验室（E 次实验，每次必须先预测；第 10、20、30 次由裁判指定动作）、提交理论（`predict.py` 加 belief）、考试（8 个目标逐个揭晓，每个只能尝试一次，期间禁止实验）、field report。每轮有两个孪生实例，A 是记忆主线，B 是用于互换测试的分支。
- 理由：
  - “先预测再观测”和互换测试采纳自 codex 方案；
  - 每 10 次实验由裁判指定动作，替代了原先单独的 quiz 机制；
  - 考试每个目标只给一次机会，因此去掉 AUCCESS。

## D-007 证书默认阈值与判定方式
- 日期：2026-11-05；状态：Accepted
- 决策：
  - C1 存在性：成功率不低于 0.8；
  - C1b 鲁棒：成功率不低于 0.6；

## D-011 证书判据的三处修正（基于摆锤夹具的实测）
- 日期：2026-11-05；状态：Accepted（修订 D-007）
- 背景：在两个随机世界里对 `fixtures/devices/pendulum_striker.py` 做 FULL 认证。
  - 步长从 0.002 s 减半后，命中解的结果偏移达到 0.5 到 1.0 倍容差，属于软接触碰撞固有的一阶误差；
  - 在整个旋钮空间里随机采样时，物块被打下桌沿的动作是混沌的，误差可达 0.5 m；
  - 名义参数的成功率在某个世界里高达 0.96，因为这次抽到的真实物性恰好接近先验中心。
- 决策：
  1. 基础步长由 0.002 s 改为 0.001 s。实测中位误差从 0.69 cm 降到 0.24 cm，最大误差从 9 cm 降到 3.1 cm，代价是耗时翻倍。改用 RK4、椭圆摩擦锥或更软的 solref 都没有改善，其中更软的 solref 甚至变得不稳定。
  2. 步长收敛检查只在 oracle 的命中解上进行，并放到 C1 之后；阈值由 0.5 倍容差改为 1.0 倍容差，即数值误差必须小于容差。旋钮空间中其他区域的混沌属于合法的物理现象，不算数值伪影。
  3. C2 名义参数必要性改为在先验上评估：所有相关未知量都从先验重新抽取。本次运行世界中的名义参数成功率只作为统计量报告。理由是“挑战是否需要学习”是设计的属性；而“这次运行凭先验能不能过”，由学习者的前测直接测量。
- 灰盒参考学习者由 least_squares 改为“拟随机粗搜索 + Nelder-Mead”。原因：接触使目标函数不光滑，导致梯度法陷入局部最小。修改后命中率由 2/8 提升到 8/8。

## D-012 必要性检验的统计功效、对偶孪生采样、互换测试适用条件
- 日期：2026-11-06；状态：Accepted
- 背景：
  - 离线闭环中，同一台摆锤装置的 C2 结果在 0.33 到 0.88 之间摆动，原因是先验上只抽了 2 到 3 个实例。
  - 大样本估计（160 次）显示，两台“合格夹具”在先验上的名义成功率其实约为 0.39 和 0.41，高于阈值，属于过易设计；之前能通过只是采样噪声。
  - “最佳固定动作覆盖率”在 64 个目标上取最大值，存在向上的选择偏差。
  - 发射台没有装置专属的隐藏量，因此孪生实例的物理完全相同，互换测试恒为 1.0，失去意义。
- 决策：
  1. C2 名义参数检验改为抽取 `prior_draws` 个先验实例，每个实例 4 个目标：FULL 为 24 个，FAST 为 16 个，TEST 为 8 个。这一步只需要仿真，开销很小。
  2. 固定动作覆盖率改在 256 个目标上计算。
  3. 孪生实例 A、B 的装置专属隐藏量采用对偶采样：两者在先验的单位坐标上相差 0.5。
  4. 若装置没有任何装置专属隐藏量，互换测试标记为“不具信息量”，并在成绩单中建议建造者加入一个。
  5. 两台夹具的目标区间上移到对隐藏量敏感的区域，容差同时收紧：摆锤为 [0.05, 0.30]、0.025，名义成功率约 0.21；发射台为 [0.55, 0.68]、0.015，名义成功率约 0.21。目标区间的低端对应“几乎不动”，这一区域对隐藏量不敏感，任何参数都能命中，这正是名义成功率偏高的根源。
- 教训：这两台“合格夹具”是我（系统作者）手写的，同样会犯“题目太易”的错误；只有统计功效足够的证书才能发现。这也从侧面说明，不能信任出题者的自觉，包括系统作者本人。

## D-013 沙箱采用手写 SBPL（sandbox-exec），而不是 srt
- 日期：2026-11-06；状态：Accepted（采用方案 1b 中的回退选项）
- 实测：
  1. SBPL 中后写的规则会覆盖先写的规则，因此可以先整体禁止、再个别放行；
  2. 子进程会继承沙箱；
  3. 嵌套 sandbox-exec 会报 "Operation not permitted"，所以两个 CLI 自带的沙箱都必须关闭；
  4. 含中文的路径可以正常匹配；
  5. `/tmp` 必须写成真实路径 `/private/tmp`。
- 决策：每个角色一份 deny-list 策略（`allow default` 加有针对性的 deny）：
  - 读取：禁止访问对方的工作区、裁判区、项目源码（学习者只放行 `claude/.venv`）、`fixtures/`、`tests/`、`docs/`、工作区根目录下其他 Agent 的方案；还有 `~/.codex`、`~/.cursor/plans`、`~/Library/Application Support/Cursor`（IDE 会话历史中含有本项目的设计讨论）；以及启动时已存在的 `~/.cursor/chats/*` 和其他 `~/.cursor/projects/*`（启动前做快照，包含对方 Agent 的会话记录）。
  - 写入：对 `$HOME` 整体禁止写，只放行自己的工作区、`~/.cursor`、`~/.local`、`~/Library/Caches`、临时目录。这样一个 Agent 无法在另一个 Agent 会读取的位置留下暗示。
- 不采用 srt 的理由：需要全局安装 npm 包；它的网络代理与 Node 编写的 cursor-agent 是否兼容尚未验证；而 deny-list 策略可以用自检逐条验证。
- 残余风险：两个 Agent 共享 `~/.cursor` 下的 CLI 配置与缓存文件，理论上构成低带宽的隐蔽信道。缓解办法：建造者与学习者顺序运行；`chats/` 和 `projects/` 中对方的目录禁读；运行结束后做 canary 审计。

## D-014 会话时间预算，以及建造者 prompt 的修订
- 日期：2026-11-06；状态：Accepted
- 背景：真实冒烟运行 `llm-smoke-1`（composer-2.5）中，建造者第一次提交被 C2 拒绝（名义成功率 0.39；它本地估计的是 0.19 到 0.28，说明设计贴着阈值）。第二次会话中，它把超时和催促的 3864 s 全部用于循环运行本地检查，始终没有再提交，这一轮因此失败。
- 决策：
  1. 每个会话都有截止时间。建造者的截止时间写入 `forge.json`，每个 `forge` 命令都会打印剩余时间，接近截止时提示立即提交。学习者的截止时间写入 `.lab.json`，`lab status` 显示剩余分钟数。催促只在剩余时间不少于 3 分钟时发起，且不再延长总时长。
  2. `forge check` 默认使用与本次运行相同的认证配置（FULL 运行时取 fast）；C2 的结果附带 Wilson 区间，区间跨过阈值时标注 BORDERLINE。
  3. 建造者 prompt 增加一条时间预算规则，并更新 `hashes.json` 中的 builder 哈希。学习者 prompt 不变。学习者工具只增加了剩余时间显示，这是通用信息，与任何装置的内容无关。学习者侧不依据任何装置内容做调整（冒烟运行中唯一的装置被拒，学习者从未接触过它）。

## D-016 封闭共享临时目录

## D-017 C3 参考学习者的可靠性：拟合预算、建造者自检与裁判一致、按拟合报告
- 日期：2026-11-06；状态：Accepted（修订 D-007、D-011 中的 C3 部分）
- 背景：`demo-1` 第 3 轮，建造者在设计日志中报告了两件事。
  1. 它做了两台新机构（飞行中释放滑块；电机通电一段时间后断电滑行），C0 到 C2 全部通过，但被 C3 参考学习者拒绝。预算从 46 加到 72 后命中反而从 1/6 降到 0/6。
  2. 同一结构在不同种子下 C3 一次 6/6、一次 1/6，“C3 被种子噪声主导”。
- 诊断（`scripts/diagnostics/c3_reference_variance.py`，第 3 轮装置，实例 A，每组 8 个种子）：

  | 参考学习者配置 | 平均命中率 | 最差一次 | 达到 0.7 的次数 |
  |---|---|---|---|
  | FAST 原预算：16 搜索点，1 次重启，24 次评估，拟合 3 个参数 | 0.65 | 0.00 | 3/8 |
  | 32 搜索点，3 次重启，80 次评估，拟合 3 个参数 | 0.88 | 0.83 | 8/8 |
  | 同上，拟合 4 个参数 | 0.94 | 0.83 | 8/8 |

  结论：方差主要来自拟合器的计算预算，而不是数据中的信息量。原配置下 C3 对可辨识的装置也会误杀。另一个结构性问题是 `reference_instances=1`：一次拟合决定所有目标的成败，目标之间高度相关，按目标计算的 Wilson 区间因此过于乐观。
- 决策：
  1. `FitBudget` 默认值改为 32 个搜索点、12 条搜索子集、20 条拟合子集、3 次重启、每次 80 次评估。这是仿真计算预算，不是实验预算，不改变参考学习者能获得的信息。
  2. FAST（建造者 `forge check` 使用）不再使用缩水的拟合预算，拟合参数数与 FULL 统一为 4 个，使建造者的自检能预测裁判的结论。
  3. FULL 做 2 次独立的参考拟合（各自独立的实验设计和噪声），证书记录每次拟合的命中（`reference_fit_hits`），拒绝信息中写明“同一次拟合内的目标共享误差”。
- 未做：没有用真值做起点或用真值评估拟合，因为那会让“原则上可学”的证明失效。
- 影响：FULL 认证每次多 1 到 2 分钟。慢速元评测（FULL）用时从 212 s 增加到 623 s，全部通过。
- 验证：从建造者会话记录中还原了它放弃的两台设计，在 demo-1 的真实世界下各用 3 个种子重新认证（C3 参考学习者命中数，满分 6）：

  | 被放弃的设计 | 修复前 | 修复后 |
  |---|---|---|
  | 释放滑块（`dwell` 旋钮，预算 72） | 5、5、2 | 5、6、5 |
  | 断电滑行（`burst` 旋钮，预算 56） | 2、6、5 | 2、4、6 |

  - “释放滑块”修复后 3 次都通过，原来属于误杀。建造者归纳的“阶段时长旋钮无法拟合”是被裁判噪声误导的结论。
  - “断电滑行”修复后仍然对种子敏感，**这个问题尚未解决**。待查的假设：相关未知量超过 4 个，未拟合的那部分固定在先验中心造成偏差。下一步是让参考学习者拟合全部相关未知量，或按 Fisher 信息自适应选择拟合维数。
  - 两台设计的 C0 到 C2 全部通过；它们沿用了第 3 轮那两个不起作用的改装尺寸，在新裁判下会被 C3 改装检验退回（D-018）。
- 后续尝试（2026-11-07，未采用）：检验“相关未知量超过 4 个”的假设。放宽上限后，“断电滑行”的相关未知量实际有 7 到 8 个，假设成立。但放宽拟合参数数并不能解决问题：

  | 配置 | 断电滑行 | 释放滑块 |
  |---|---|---|
  | 拟合 4 个参数（现行） | 2、4、6 | 5、6、5 |
  | 拟合至多 8 个参数 | 5、4、5 | 6、2、4 |
  | 至多 8 个参数，搜索点和评估次数加倍 | 5、4、5 | 6、2、4 |

  - 参数少了模型设定有偏差，参数多了优化更难，两者此消彼长。
  - 加倍评估次数后结果逐个种子都不变，说明 Nelder-Mead 在原预算内已经收敛到局部最优，瓶颈不在计算量。
  - 结论：保持拟合 4 个参数。剩下的不稳定需要更好的拟合方法（例如从分散的起点多次重启、按 Fisher 信息分组拟合），或者说明这类设计在当前预算下确实难以辨识。留作未解决项。
  - 走过的弯路：一开始用 `c3_reference_variance.py --keys 8` 在 demo-1 的装置上比较，但该脚本只能使用证书里记录的相关参数清单（只有 4 个），`--keys 8` 没有生效，两组输出完全相同。已给脚本加上警告；比较改用 `recertify.py --keys`。

## D-018 改装检验必须有区分力
- 日期：2026-11-06；状态：Accepted
- 背景：`demo-1` 第 3 轮的对照项显示 `stop_post.posx` 的改装影响为 0.0 倍容差。复现发现，挡块外移超过约 -0.045 后，撞杆就扫不到它，摆臂改由铰链限位停下，结果不再随挡块位置变化。这时“忽略改装”的黑盒反而得分，而按物理推理预测变化的学习者被打上 `modification_fail`。第 2 轮的 `striker.posz` 也只有 0.63 倍容差。原裁判只在对照项里如实报告了这个数，没有据此判定考题无效。
- 原则：改装让结果移动的幅度要明显超过一个容差，“忽略改装”的预测才会失分，考题才能区分物理模型和曲线拟合。阈值取 1.5 倍容差（中位数）。
- 决策：
  1. 认证新增 C3 改装检验：对每个声明的可改装尺寸，在裁判的检验点（向较远边界移动 80%）测量结果变化，低于阈值则退回，并给出修改建议（换一个仍有影响的范围，或删掉该尺寸）。未声明可改装尺寸时不检验。
  2. 运行时，每组改装考题记录实测影响 `effect_over_tol`。无区分力的考题照常报告分数，但标注 `non-discriminating`，不计入 `modification_fail`；成绩单在指导中点名不起作用的尺寸。
  3. 元评测新增作弊装置“不起作用的改装尺寸”（发射台上沿 y 方向移动钢球：推杆端面是平的，落点 x 不变），必须在 C3 改装检验被拦下。
- 附带发现：我手写的合格夹具 `pendulum_striker` 的 `block.posx`（-0.232 到 -0.19）在检验点只有 0.44 倍容差，同样没有区分力。原因是两个效应相互抵消：块右移使起点变远，但摆锤过了最低点才撞上它，冲量变小。范围改为 -0.232 到 -0.10 后，6 个实例上的影响都在 5.5 倍容差以上。离线脚本建造者的同款装置一并修改。这是继 D-012 之后，系统作者自己的“合格”设计第二次被证书拦下。

## D-019 基础设施故障不计为 Agent 的失败
- 日期：2026-11-06；状态：Accepted
- 背景：对照运行 `demo-1-weak` 和 `demo-1-amnesic` 并行进行时，本机网络在 18:42 前后中断。此后启动的会话都在 1 到 3 秒内退出，stderr 为 `Error: [unavailable] getaddrinfo ENOTFOUND api2.cursor.sh`。编排器把这些会话照常计分为考试 0%，导致两组对照从第 2 轮起全部作废，而且数据表面上像“学习者失败”。

  1. 后端识别基础设施错误：本次运行退出码非 0，且新增的 stderr 中出现网络或服务类标记（`[unavailable]`、`ENOTFOUND`、`ECONNRESET` 等）。

- 补充（2026-11-09）：`demo-2` 第 5 轮暴露了两个漏洞。
  - 04:00 笔记本合盖、靠电池（电量 11%）进入睡眠，建造者会话中断。stderr 只有 `RetriableError: Connection stalled repeatedly`，不在错误标记表里；会话因此没有重试，也没有标为无效，而被记成“建造者没交出设计”。
  - macOS 睡眠期间，子进程超时用的单调时钟不走，墙上时钟照常走，所以 1920 s 的时限没有触发，会话实际持续了 4123 s。

## D-020 C3 参考学习者：四次改法的结果，以及补上灰区加测
- 日期：2026-11-09；状态：灰区加测 Superseded by D-022（参考学习者改为警告后不再影响判定，加测关闭，代码保留）；其余改法均未采用
- 背景：D-017 之后，参考学习者仍会拒掉信息量足够的设计。`demo-2` 第 4 轮，建造者给推杆滑座加了一个隐藏质量，在 4 个本地世界中参考学习者只命中 2/6、4/6、3/6、1/6，而 Fisher 检验显示后验预测不确定度只有 0.002 到 0.024 倍容差。建造者的判断是：“信息就在数据里，只是一次拟合在这个预算下找不到。”同一缺陷第二次限制了升级方向。
- 试过的改法（FAST，每组 3 个种子，单次拟合命中数，满分 6）：

  | 改法 | 滑座加质量 | 断电滑行 | 回归：demo-1 第 3 轮装置 |
  |---|---|---|---|
  | 现行（D-017） | 5、4、2 | 2、4、6 | 平均 0.92，6/6 达标 |
  | 拟合至多 8 个参数 | — | 5、4、5 | — |
  | 精细拟合用全部实验 | 6、6、1 | 6、4、6 | 平均 0.75，3/6 达标 |
  | 全部实验，64 个搜索点，5 次重启 | 6、6、1 | 6、4、6 | — |

  - 每种改法都是有的装置变好、有的变差；加大搜索和重启次数后结果逐个种子不变，说明不是计算量问题。
  - 判断：参考学习者是一个启发式优化器，在这几台设计上单次拟合的真实成功率约为 0.6 到 0.8，正好压在 0.7 的阈值上。
- 决策：补上 D-007 规定、实现时漏掉的灰区加测。C3 参考学习者原来用点估计硬切；现在先做计划的拟合次数（FULL 2 次，FAST 1 次），合并后的 Wilson 区间跨过阈值时追加独立拟合（FULL 最多 2 次，FAST 最多 1 次），加满仍不明确再按点估计判定。
  - 加测后的结果（每组 3 个种子，合并 2 次拟合）：滑座加质量通过 1/3，断电滑行通过 1/3，释放滑块通过 2/3（原单次拟合 3/3）。判定没有变宽松，只是不再取决于一次拟合的运气。“释放滑块”从 3/3 变成 2/3，说明之前全过有运气成分。
  - 代价：FAST 下单次拟合 6 个目标的 Wilson 区间很宽，除非首次拟合惨败，几乎总会追加第二次，建造者每次自检多约 1 分钟。
- 遗留（裁判最主要的未解决问题）：参考学习者的能力上限限制了建造者能出的题。我从未构造“不可辨识”类的作弊装置，0.7 这个阈值缺乏元评测依据。可能的方向：让参考学习者按 Fisher 信息分组拟合；或把 C3 改为“Fisher 检验为主、参考学习者为辅”，参考学习者只在 Fisher 检验通过但结果接近阈值时作为警告。

## D-021 学习者工单发现的两个接口缺陷
- 日期：2026-11-09；状态：Accepted
- 背景：`demo-2` 第 2 轮起，建造者的坡道设计带有“失速悬崖”，部分实验的结果是 `no_landing`。第 3、4 轮学习者提交了三张工单：
  - `ambiguous_spec`：协议要求预测是一组浮点数，没有办法预测“不会落地”，`null` 和 `[null]` 都被拒绝；
  - `interface_bug`（两张）：`probe-result` 的预测校验失败时，等待中的探针会被清掉，必须重新申请。
- 决策：
  1. 预测可以为 `null`，表示“预计没有有效结果”。说明书规则、`lab` 的帮助文字同步说明；理论文件 `predict` 也可以返回 `None`。
  2. 评分：预测 `null` 且确实无有效结果，误差记为 0；一边有结果、一边没有，记为一次 `outcome_kind_misses`，单独计数，而不是悄悄排除。
  3. `probe-result` 先校验预测，校验通过后才消耗探针。
- 这是通用接口修复，适用于任何会出现“不落地、不停止”状态的装置，不依据任何具体装置的内容；学习者提示词不变，哈希不变。
- 反思：设计接口时我默认“总会有一个落点”，这个假设在建造者开始设计分段机制后就不成立了。两个问题都是被评测的学习者通过工单通道发现的。

## D-022 C3 以 Fisher 可辨识性检验为门槛，参考学习者降为警告
- 日期：2026-11-09；状态：Accepted（用户在“调整 C3 规则 / 改进参考学习者 / 不改直接跑 / 到此为止”中选择了前者，条件是先用“不可辨识”作弊装置做元评测）
- 我的顾虑：Fisher 检验在 demo 中几乎总是 0.000 到 0.02 倍容差，我怀疑它在当前实现下什么都能通过。它假设学习者已知结构、只在真值附近做局部线性近似，而且把所有传感器轨迹都当作观测。
- 实验：把 demo-2 第 4 轮的认证装置改成“预算 10 次、去掉所有传感器、只看落点”（3 个旋钮、约 5 个相关未知量）。

  | 装置 | Fisher 检验（门槛 0.5 倍容差） | 参考学习者（门槛 0.7） |
  |---|---|---|
  | 原版（54 次实验，有传感器），demo-2 世界 | 0.009、0.011，通过 | 11/12、12/12，通过 |
  | 作弊版，demo-2 世界 | 1.63、1.34，**两次都拦住** | 9/12（**放行**）、5/12（拦住） |
  | 原版，元评测世界（种子 7，TEST 配置） | 0.006、0.012，通过 | — |
  | 作弊版，元评测世界 | 0.79、1.74，两次都拦住 | — |

  结论与顾虑相反：Fisher 检验对传感器和预算很敏感，能可靠拦下“预算内不可辨识”的设计；demo 中数值接近 0，是因为那些装置的信息量本来就足够。参考学习者既会误拒（D-017、D-020 中信息足够的设计），也会误放（上表），不适合当硬门槛。
- 决策：
  1. C3 的门槛是 Fisher 后验预测检验（阈值不变，0.5 倍容差）。
  2. 参考学习者照常运行，结果写进证书和成绩单；低于 0.7 时判定为 `warn`（不阻止认证），提示“任务可能难以在预算内学会”。灰区加测随之关闭（`reference_extra_fits=0`），代码保留。
  3. 元评测新增作弊装置“预算内不可辨识”（上表的作弊版，夹具 `fixtures/devices/gated_ramp_launcher.json` 取自 demo-2 建造者的设计），必须在 Fisher 检验这一步被拦下；同一装置的完整版作为阳性对照，必须通过。
- 附带修复（改装检验的误拒）：同一实验中，原版装置在一个种子下被改装检验以“给不出有效结果”拒绝。原因有二：检验在整个旋钮空间随机取 6 个点，而这台装置有大片区域球冲不上坡，6 个点可能全部没有有效结果；“改装前落地、改装后不落地”这种结果类型的变化被当作缺失数据排除了。修复：认证时在解题器的解上测量（它们在目标区域里，能产生有效结果，也正是考试关心的区域）；结果类型变化计为 10 倍容差。
- 残余风险：Fisher 检验是局部的，并假设结构已知。对于全局多峰、或强非线性使局部近似失效的设计，它可能放行实际难学的题；这时参考学习者的警告和学习者的 `suspected_unsolvable` 工单是第二道防线。

  2. **代码放在 `mlab/` 之外**（Python 在 `observatory/`，前端在 `web/`）。建造者的沙箱可以读 `mlab/`，观察窗的接口和令牌文件位置不应出现在 Agent 可读的范围内；这样在 demo-3 运行期间新增代码，也不会改变 Agent 能看到的东西。与计划的偏差：原计划放在 `mlab/analysis/` 并接入 `mlab viz` 子命令。
  3. **访问控制。** Agent 沙箱允许联网（要调模型 API），所以本机任何端口对它们都可达。服务只绑定 `127.0.0.1`；每个数据请求都要带令牌（进程内生成 32 字节，写入权限 0600 的文件并打印到用户终端，不进命令行参数和环境变量）；校验 Host 头以防 DNS 重绑定；不返回 CORS 头。运行结束后，把发过的令牌当作 canary 扫描两侧的工作区和会话记录，结果作为 `audit` 事件显示在页面上。
  4. **真值显示。** “上帝视角”开关控制真值（世界参数、实例参数、无噪声结果、真值曲线）是否显示，直播时默认关闭。静态包只为已结束的运行导出（导出会拒绝未结束的运行），写入 `demo/recorded/<run_id>/viz/`；它和 `index.md` 已公开的世界真值属于同一级别的交付物。
  5. **诚实性。** 3D 回放是无执行噪声的重演，标注为“意图重演”，并叠加学习者实际观测到的落点。所有指标来自裁判文件或裁判侧重新仿真；学习者的自述（笔记、`belief.json`、理论）用专门的信号色标出。学习者的 `predict.py` 在 theory 沙箱（无网络、只读自己的临时目录）里执行。导览字幕由运行数据按模板生成。
  6. **工具链。** 前端用 Vite、React、TypeScript、three.js（`@react-three/fiber`、drei）和 d3；Python 侧只用标准库的 HTTP 和 SSE，不新增 Python 依赖。
- 验证：`tests/test_observatory.py` 6 项（扫描增长中的运行目录、等待写了一半的行、孪生副本不重复计数；重演与直接仿真一致；拒绝导出未结束的运行；令牌审计；无令牌 401、错误 Host 421、路径穿越 404）。对正在运行的 demo-3 只读联调：SSE 实时推送、按需重演约 30 ms、曲线先 202 后 200。
- 残余风险：用户把带令牌的链接粘进 Agent 会话，令牌就会泄露（运行结束后的审计能发现）；页面同屏显示双方的信息，只能给人看。
